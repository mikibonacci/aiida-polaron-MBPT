# Examples

Two launch scripts live in [`examples/`](https://github.com/mikibonacci/aiida-polaron-MBPT/tree/main/examples). Both submit the same calculation: a two-atom silicon cell, with a different Hubbard U on each atom, through the three relaxations and the Yambo GW/BSE step. They differ only in how the Yambo part is configured.

| | [`launch_polaron_mbpt.py`](https://github.com/mikibonacci/aiida-polaron-MBPT/blob/main/examples/launch_polaron_mbpt.py) | [`launch_polaron_mbpt_high_level.py`](https://github.com/mikibonacci/aiida-polaron-MBPT/blob/main/examples/launch_polaron_mbpt_high_level.py) |
|---|---|---|
| Yambo inputs | Written by hand as `Dict` nodes | Generated by the `aiida-yambo` high-level API |
| Needs a Yambo protocol | No | Yes (`get_builder_from_protocol`) |
| Length | Longer, everything is explicit | Shorter, set through methods such as `set_Nb` |
| Best for | Seeing exactly which inputs reach the workflow | Changing a few settings on top of a protocol |

## Shared parts

Both scripts follow the same steps. Edit the code labels and the pseudo family before running them.

1. **Structure.** `make_structure()` builds diamond silicon with the kinds `Si1` and `Si2`. The two atoms are different kinds so that they can get different U values.
2. **QE parameters.** `make_relax_parameters()` returns the `relax` parameters (cutoffs, `bfgs`, convergence thresholds). The same `Dict` is used for `relax_1`, `relax_2` and `relax_3`.
3. **K-points.** A 1×1×1 mesh for `kpoints_gamma`, and a 2×2×2 mesh for `kpoints_relax3` and `kpoints_yambo`.
4. **Hubbard U.** `Si1` gets 2.0 eV in both dictionaries. `Si2` goes from 10.0 eV in `hubbard_u_initial` to 2.0 eV in `hubbard_u_final`, so the second relaxation starts from a different U than the first. The values are only an illustration.
5. **Resources.** The same `metadata.options` are set on each relaxation.
6. **Submit.** `submit(builder)` and print the PK.

## `launch_polaron_mbpt.py`: explicit inputs

The Yambo namespace is filled by hand, one node at a time:

```python
builder.yambo.scf.pw.parameters = orm.Dict(dict={...})
builder.yambo.nscf.pw.parameters = orm.Dict(dict={...})
builder.yambo.qp.yambo.parameters = orm.Dict(
    dict={
        "arguments": ["dipoles", "HF_and_locXC", "gw0", "ppa"],
        "variables": {"NGsBlkXp": [2, "Ry"], "BndsRnXp": [[1, 16], ""], ...},
    }
)
builder.yambo.bse.yambo.parameters = orm.Dict(dict={...})
builder.yambo.QP_subsets_dict = orm.Dict(dict={"range_QP": 5.0, ...})
```

You write the SCF and NSCF QE parameters, the Yambo `arguments` and `variables` for GW (`qp`) and BSE (`bse`), the resources, the `settings` (`INITIALISE` and `COPY_DBS` set to `False`) and the QP subsets. The workflow itself provides the structure, codes, pseudopotentials and k-points, so you do not set them under `builder.yambo`.

## `launch_polaron_mbpt_high_level.py`: protocol and input manager

Here the Yambo part is built by `configure_yambo_from_protocol`, in three steps:

1. `YamboWorkflow.get_builder_from_protocol(...)` creates a complete builder from a protocol (`moderate`, `bse@qp`, insulator, no spin).
2. A `YamboInputManager` wraps it, and you change only what you need:

    ```python
    manager.scf.set_kmesh([2, 2, 2])
    manager.set_nscf_nbnd(32)
    manager.qp.set_Nb(value=16, add_if_not_present=True)
    manager.bse.set_BSEbands([3, 6])
    manager.set_QP_subsets_dict(range_QP=5.0, range_spectrum=10.0, qp_per_subset=16, parallel_runs=1)
    ```

3. The generated inputs are copied into `builder.yambo`. Only the configurable leaves are copied (`parameters`, `settings`, `parallelization`, `metadata`). The structure, codes, pseudopotentials and k-points are left out because the outer workflow supplies them from the stage-3 structure.

The helper `_copy_yambo_leaf` does the filtering. The protocol also needs the structure, the three codes and the pseudo family, so those are passed to `configure_yambo_from_protocol` too.

!!! note
    Both scripts set `builder.yambo.stop_if_metal = True`, which stops the Yambo workflow if the system turns out to be metallic. Only the high-level script also sets `additional_parsing = ["gap_", "lowest_exciton"]`, which asks the workflow to parse the gap and the lowest exciton from the results.

## Running an example

```bash
verdi run examples/launch_polaron_mbpt.py
# or
verdi run examples/launch_polaron_mbpt_high_level.py
```

Follow the progress with `verdi process list` and `verdi process report <pk>`.
